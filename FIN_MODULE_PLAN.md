# fin module — development plan

## Context

`Core` (access control) is the module we've built the frontend against so far, phase by phase. Guardian-back also has an entirely separate, untouched `fin` namespace — ~38 controllers implementing a full condo/HOA accounting system (charges, billing, cash/bank, cheques, payroll, journal/ledger, reporting). This is roughly the same size as everything built in `Core` so far, maybe bigger. This document maps it out and proposes a phased build order, based on a deep read of every controller/DTO/SaveModel in the namespace plus a skim of each business component's validation logic.

**Headline finding: no backend bugs found anywhere in `fin`.** Every `SaveModel → Dto` AutoMapper map exists, and every `UpdateAsync` correctly looks up its target row by `Ids = [entity.Id]` (the exact bug class we found twice in Core — wrong lookup key — does not recur here). This module reads as more carefully written than Core was before our fixes.

**Caveat:** the dev SQL Server was unreachable while researching (connection timeouts), so row counts for `fin.*` tables are unverified. Re-check before starting Phase 1 — if `fin.Account`/`fin.CostCategory`/`fin.PostingRule*` already have system-seeded rows, that changes what Phase 1 actually needs to build.

## How the module is shaped

Every "posted form" entity (ChargeIssue, Receipt, PartyPayment, CashTransfer, FundTransfer, UnidentifiedDeposit, ChequeFate, ServiceBilling, BuildingDepositMovement, Payroll, LateFeeRun, OpeningBalance, ExpenseInvoice once posted) follows **double-entry bookkeeping discipline, not CRUD**: `Add` posts and generates a `JournalEntry`; there is no `Update`; `Cancel` reverses via a reversing journal entry. The frontend shape for these needs to be list + read-only detail + "new document" form + "Cancel" action — not the Add/Edit dialog pattern used everywhere in Core.

A few entities are **read-only on their own controller, written only as a nested part of another entity's save** — same pattern as `ElevatorFloor`/`Cabinet` in Core:
- `JournalLine` (written via `JournalEntry`'s save)
- `PostingRule`/`PostingRuleLine`/`PostingRuleLineDimension` (system-seeded auto-posting templates — skip entirely, not a frontend task)
- `ChequeStatusHistory` (audit trail)
- `Receivable` (only `Search`/`GetById`/`Cancel` — generated by `ChargeIssue`/`ServiceBilling`/`LateFeeRun`, settled via `Receipt.Allocations`)

`FinAttachment` is a generic reusable attachment component (like Core's `Attachment`) scoped to specific fin entity types (ExpenseInvoice, Receipt, Cheque, Contract, JournalEntry, OpeningBalance, Forgiveness, BuildingDeposit) — wire it into each entity's detail page as that entity gets built, not a separate phase.

`FinReport` is a pure reporting layer (statements, debtors, budget-vs-actual, trial balance, ledger, annual report, cheques report, party ledger) sitting on top of everything else — build last, once there's real data to report on.

## End-to-end cycle: one month's charge, from issue to cash

Traced the full path through `ChargeIssuingComponent`/`ReceiptComponent`/`ReceivableComponent` to confirm how the pieces actually connect at runtime:

1. **Setup (once):** `QuickSetup` → `AccountingEntity` + `FiscalYear` + `CashAccount` + `ChargePlan` + `ChargeComponent`(s) exist (Phase 1, resolved above).
2. **Monthly run:** `ChargeIssueController.Preview` (dry run, no writes, no Party creation) lets the manager check the numbers before committing; `Add` actually posts. One `Receivable` + one journal entry **per payer per unit/space** (deliberately split — "so cancelling one doesn't break the rest," per the component's own doc comment), built from the `ChargePlan`'s `ChargeComponent`/`ChargeCoefficient`/`ChargeDiscount` configuration snapshotted at issue time (so later editing the plan never retroactively changes a past issue).
3. **Party resolution happens inside the real `Add`, not `Preview`:** for every payer-person without an existing `Party`, one is auto-created (`PartyType = Natural`, linked to that `PersonId`) — confirmed by reading `ChargeIssueBuildReceivablesAsync`. No manual "create Party" step for residents.
4. **Posting is generic, not per-entity:** `ChargeIssueAddAsync` builds a `DtoPostingRequest` (document type + a bag of `PostingVariableEnumeration` values: Amount/Party/ChargeableItem/Building/Fund + per-component `Items`) and hands it to `PostingComponent.PostingBuildManyAsync`, which resolves the actual debit/credit `Account` lines using the system-seeded `PostingRule` templates (the 28 rows confirmed in the DB). **Every other posted-form entity in this module works the same way** — same `PostingRequest` shape, different `DocumentType`/variables — so once this generic engine is understood for `ChargeIssue`, it's the same mechanism for `Receipt`, `PartyPayment`, `CashTransfer`, etc. `PostingRule` itself stays fully out of frontend scope.
5. **If `RunLateFee` was requested**, overdue receivables as of the issue date get late fees calculated (and, on `Add`, posted) in the same call — or this can run separately later via `LateFeeRunController`.
6. **Resident pays:** a `Receipt` is entered (`ReceiptKind = Collection`) against that `Party` + `CashAccount`, with either explicit `Allocations` (pick which `Receivable`s it settles) or `AutoAllocate = true`. `ReceivableComponent.ReceivableBuildAllocationsAsync` is the **shared allocation engine** — also used by `PartyPayment` on the payee side — so this logic is written once and reused.
7. **Overpayment handling is automatic across periods:** any amount beyond what the `Allocations` cover becomes a negative `Overpayment`-kind `Receivable` sitting as a credit on that `Party`; the *next* `ChargeIssue` for that party automatically nets it against the new charge (per `ChargeIssueAddAsync`'s own doc comment) — no frontend logic needed to carry a credit balance forward.
8. **Unwinding:** `Receipt.Cancel` reverses via a reversing journal entry (never edits/deletes); `ChargeIssue.Cancel` cancels *every* active receivable from that issue the same way. `Forgiveness` is the alternative ending for a receivable that will never be paid — write it off, cost reallocated back to the funds it originally fed.
9. **Visibility:** `FinReport`'s statement/debtor/party-ledger endpoints and `Receivable`'s own read-only search are how a manager (or a resident, via `MyStatementGridView`) sees the running balance — there's no "balance" field anywhere that's stored and updated; it's always derived from open `Receivable`s minus `Allocations`.

This confirms the phase order isn't just an FK-dependency chart — it's a real pipeline where step 2 feeds step 6's inputs, and step 4's generic posting engine means **Phase 2 (ChargeIssue) is the first entity where the "does posting actually work end-to-end" risk gets retired** — everything after it (Receipt, PartyPayment, etc.) reuses the same already-proven posting path.

## Proposed phase order

### Phase 1 — Accounting foundation (everything else depends on this)

**Resolved — build the `QuickSetup` wizard, skip hand-built foundation CRUD.** Checked the dev DB directly: `fin.Account` (chart of accounts) already has 20 seeded rows, `fin.PostingRule` has 28, and the two system `Fund` rows (`OperatingFundId`/`ReserveFundId`) plus the default `CostCategory` that `FinSetupComponent.QuickSetupAsync` hardcodes by GUID all already exist, flagged `IsSystem`. These are backend/DB-migration-seeded reference data — not something a frontend CRUD screen should expose (the backend itself blocks editing `IsSystem` rows' protected fields). `AccountingEntity`/`CashAccount`/`ChargePlan` are all empty — a fresh, unconfigured system, exactly what `QuickSetup` is for.

`POST /api/fin/FinSetup/QuickSetup` (`FinQuickSetupModel`) creates, in one transactional call (rolls back every step on failure since nothing posted yet is a real ledger document):
- `AccountingEntity` (Title + the `BuildingIds` to link — rejects any building already linked to another entity, 38101)
- `FiscalYear` (+ auto-generated `FiscalPeriod` rows)
- `CashAccount` (type=Bank; Title/BankName/AccountNumber/Sheba)
- `ChargePlan` (DueDay/GraceDays/LateFeeMode/Rate, Fund IDs wired to the system Operating fund, RoundingUnit=1000)
- `ChargeComponent`s — caller-supplied, or if empty: a default "شارژ ماهانه" (monthly, by area, resident-paid) and, if `MonthlyReserveAmount > 0`, a "ذخیره" (reserve, equal-split, owner-paid) component
- 4 default `ServiceBillingType` rows (duplicate card, duplicate remote, common-area damage, common-space reservation) — editable/deletable afterward

So **one wizard screen replaces hand-building AccountingEntity + FiscalYear + CashAccount + ChargePlan + ChargeComponent + ServiceBillingType screens** for the initial setup. (`ChargePlan`/`ChargeComponent`/etc. still need their own normal CRUD screens later for *editing* after the wizard runs — Phase 2 below — QuickSetup only short-circuits the one-time bootstrap.)

Two follow-up actions complete onboarding (separate endpoints, same controller):
- `POST /api/fin/FinSetup/ResidentUsers` (`buildingIds`, `userGroupId`, `password`) — bulk-creates logins for every contract principal in those buildings without one yet; login info goes out via the event/notification module, not returned in the response.
- `POST /api/fin/FinSetup/MenuBundleApply` (`userGroupId`, `bundle`) — grants a `UserGroup` a named menu-permission bundle in one call instead of ticking 100+ menu checkboxes by hand: `BuildingManager`(1)/`Observer`(2, read-only reports)/`Accountant`(3, advanced-mode only)/`Resident`(4, forces `AccessType = OnlySelf`, grants only "my statement"). `GET /api/fin/FinSetup/MenuBundles` lists what each bundle actually contains, for a preview before applying.
- `GET`/`POST /api/fin/FinSetup/NumberFormats` — document numbering templates per fin entity type; has sane defaults, safe to defer/skip initially.

**Resolved — `Party` auto-creates itself, no manual step needed for residents.** Traced `ChargeIssuingComponent.ChargeIssueBuildReceivablesAsync`: when a real issue runs (`createParties: true`, not during `Preview`), it looks up each payer-person's existing `Party` by `PersonId` and, if missing, calls `PartyComponent.PartyAddAsync` itself to create a `Natural`-type `Party` on the fly. Residents never need a manual "create Party" step — only vendor/payee Parties for `ExpenseInvoice`/`PartyPayment` (people not tied to a unit-occupancy contract) would ever need `PartyController`'s own CRUD screen.

### Phase 2 — Charges & the monthly billing cycle
`ServiceBillingType` (catalog, build first) → `ChargePlan` → `ChargeComponent` → `ChargeCoefficient`/`ChargeDiscount` (parent chain) → `ChargeIssue` (the monthly run — Preview/Add/Cancel only, immutable once posted) → `LateFeeRun` (needs ChargeIssue's receivables to exist first) → `ServiceBilling` (ad-hoc charges, needs ServiceBillingType).

Reuses Core's `BuildingUnit`/`BuildingSpace` pickers directly (`ChargeDiscount`, `ServiceBilling` reference them).

### Phase 3 — Expenses & building-side adjustments (parallel with Phase 2, same foundation deps)
`ExpenseInvoice` (the one entity here with a real draft state — Add/Update/Delete while draft, Cancel once posted) and `BuildingDeposit`(+`BuildingDepositMovement`) can be built any time after Phase 1; independent of Phase 2.

### Phase 4 — Cash, bank, cheques & payments
`Fund`, `CashAccount` (master data, needs only Phase 1) → `Cheque` (full CRUD, status starts Pending — "status-change not implemented this phase" per the backend's own comment) → `CashTransfer`/`FundTransfer` (between CashAccounts/Funds) → `UnidentifiedDeposit` → `Receipt` (needs open `Receivable`s from Phase 2, so sequence after it) → `ChequeFate` (drives Cheque.Status; realistically enters cheques via Receipt/PartyPayment's nested lists rather than standalone) → `PartyPayment` (needs open `ExpenseInvoice`s from Phase 3) → `Payroll` (needs only `Fund`, can slot in anywhere after it).

### Phase 5 — Write-offs, reporting & visibility
`Forgiveness` (needs receivables from Phase 2/3 — build last). `FinReport`'s statements/debtors/budget/trial-balance/ledger/annual reports. A read-only `JournalEntry`/`JournalLine` ledger viewer (manual journal-entry authoring is "advanced mode only" and lower priority). `Receivable`/`ChequeStatusHistory` surfaced inline on the relevant detail pages (Party ledger, Cheque detail) rather than as standalone list pages.

## Scope sizing

~38 controllers across 5 phases, each phase comparable in size to one or two of the Core modules already built (Contract, Elevator, CabinetRoom). This is realistically a multi-session effort on its own, separate from any remaining Core work.
